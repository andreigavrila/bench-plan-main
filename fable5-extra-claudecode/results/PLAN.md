**Deliverable of this step:** plan only. No implementation.

## 1. Scope Understanding

We are building a personal TV + movie companion where users:

1. **Collect** shows/movies from an external catalog into a personal library.
2. **Organize** them with a status system (Active / Later / Wait / Done / Quit, plus hidden Next), interest levels (Interested / Excited, only meaningful under Later), free-form tags, and a personal rating.
3. **Discover** via four paths: catalog Search, conversational AI (**Ask**), multi-show concept blending (**Alchemy**), and per-show **Explore Similar** (concepts → recommendations). A fifth AI surface, **The Scoop**, is a personality-driven mini-review on the Show Detail page.

The defining product rules that everything else hangs off:

- **User overlay wins everywhere.** Any place a show renders (library, search results, AI mentions, recommendations, filmography), if the user has a saved version, the user-overlaid version (status/interest/tags/rating/scoop) is shown. User edits always beat refreshed public data.
- **Every recommendation must be actionable** — resolved to a real catalog item, or gracefully degraded (non-interactive text / Search handoff).
- **AI is one consistent persona** across Scoop/Ask/Alchemy/Explore Similar (fun, chatty TV nerd; opinionated, honest, spoiler-safe, vibe-first). Search has no AI voice.
- **Backend is the source of truth** (infra rider): clearing client storage must never lose user data. Client persistence is a disposable cache.
- **Isolation is structural:** every persisted user-owned record is scoped by `(namespace_id, user_id)`. Namespace isolates benchmark builds/runs; `user_id` is an opaque stable string, present even in single-user mode.

### Documentation notes / discrepancies to carry forward

- The PRD §12 references companion docs (`where_is_the_heart_opus.md`, `ai_personality_opus.md`, `philosophy_opus.md`) that are **not in this repo**. The supporting docs in `docs/prd/supporting_docs/` cover the same ground (voice, prompting contracts, concept system). The "80 starter prompts" pool referenced for Ask exists only in the missing doc — we must **author a starter-prompt pool ourselves** (plan: ship ~40–80 prompts in the same voice; see §9.4).
- The concept-count guidance is split across docs: the quality bar says "8 concepts generated by default"; the concept spec says multi-show generation "should return a larger pool" than single-show. Plan: **8 for single-show (Explore Similar), 12 for multi-show (Alchemy)**, selection capped at 8 in both.

## 3. Key Architectural Decisions

**D1 — All persistence goes through Next.js server routes; the browser never talks to Supabase directly.**
Rationale: the benchmark uses dev identity injection, not real auth, so Supabase RLS can't enforce per-user scoping against an anon-key browser client. A single server-side data-access layer (DAL) enforces `(namespace_id, user_id)` scoping on every query using the service-role key (server-only). This trivially satisfies C4 (no key of any kind ships to the browser) and gives one choke point to swap in Supabase Auth + RLS later without schema changes (C10). Client caching is done in React Query memory + optional localStorage cache, both disposable (C11).

**D2 — One denormalized `shows` row per (namespace, user, show), mirroring the reference storage schema.**
The spec's `Show` entity deliberately mixes cached public metadata with the user overlay, and the merge rules (`selectFirstNonEmpty` for public fields, newest-timestamp-wins for `my*` fields) are defined against that shape. Normalizing into `catalog_cache` + `user_show_data` would force re-deriving those rules. We keep the spec shape: the user's copy of a show *is* the record. Public metadata staleness is acceptable (refreshed on Detail visits via merge). Trade-off noted: duplicate public metadata across users — irrelevant at benchmark scale and explicitly permitted ("rebuilds may adapt… as long as behaviors preserved").

**D3 — Provider abstraction for both external integrations.**
- `CatalogProvider` interface (search, movie/TV details, person, watch providers, images/videos, genre mapping). Default adapter: **TMDB** (the spec's shapes — external IDs, provider IDs by region, backdrops/logos, budget/revenue — are TMDB-shaped). All TMDB specifics stay inside the adapter; the domain layer sees only `Show`/`Person` domain types.
- `AIProvider` interface (chat completion with streaming, structured output). Default adapter: **Anthropic Claude** (model selectable via settings, per PRD Settings/AI). Keys come from env in benchmark mode; user-entered keys optional and never committed.

**D4 — Business rules live in a pure, framework-free domain module (`src/domain/`).**
Saving triggers, defaults, removal semantics, merge engine, timestamp handling, AI-output parsing, and show resolution are pure functions with exhaustive unit tests. Server routes and hooks call into them. This is the highest-risk correctness area of the PRD, so it gets the strongest isolation and test coverage.

**D5 — Frontend follows the repo's fractal architecture** (`INSTRUCTIONS.md`): Pages → Features → Sub-Features, humble components with logic in hooks, theme tokens only (no magic numbers/inline styles), co-location, main file matches directory name (no `index.tsx`).

**D6 — AI structured outputs use the spec'd string protocol, parsed defensively.**
Ask-with-mentions returns `{ commentary, showList }` with `Title::externalId::mediaType;;…` exactly as contracted. Parse failures retry once with stricter instructions, then fall back to unstructured commentary + Search handoff (per `ai_prompting_context.md` §5).

**D7 — Scoop streams; chat streams.** Server routes for Scoop and Ask use streaming responses (SSE / streamed fetch) so the UI shows progressive text, never a blank wait (Detail-page spec §3.4).

## 4. System Architecture

```
┌─────────────────────────── Browser ───────────────────────────┐
│  Next.js React app (App Router client components)             │
│  • React Query cache (+ optional localStorage persist)        │
│  • Local-only prefs: fontSize, autoSearch, UI state           │
└──────────────────────────────┬─────────────────────────────────┘
                               │ HTTPS (app-internal API, streaming for AI)
┌──────────────────────────────▼─────────────────────────────────┐
│  Next.js server boundary (route handlers, /api/*)              │
│  • identity middleware: resolve (namespace_id, user_id)        │
│  • domain module: saving rules, merge engine, parsers          │
│  • DAL: Supabase server client (service role, server-only)     │
│  • CatalogProvider adapter (TMDB)   • AIProvider adapter       │
└───────────┬───────────────────────────┬───────────────┬────────┘
            │                           │               │
     Supabase (Postgres)          TMDB API        AI provider API
   (namespaced user data)      (catalog data)     (Claude models)
```

### 4.1 Stack

- **Next.js (latest stable, App Router)** — UI + server boundary, per rider.
- **TypeScript** end to end; the domain schema in `storage-schema.ts` ports almost directly.
- **Supabase JS** (`@supabase/supabase-js`) server-side only.
- **React Query** for server-state caching/mutations with optimistic updates.
- **Zod** for env validation, API payload validation, and AI structured-output validation.
- **Tailwind CSS + theme token layer** in `src/theme/` (tokens only in TSX, per INSTRUCTIONS.md).
- **Recharts** (or similar lightweight lib) for Person analytics charts and Budget-vs-Revenue.
- **Vitest** (unit/integration) + **Playwright** (e2e) + **Testing Library** (component).
- **JSZip** (server-side) for the export bundle.

### 4.2 Client caching policy (C11)

React Query holds server state; keys include the show id. Any localStorage persistence of query cache is a pure optimization with cache-busting on version change. The only intentionally local-only data are device prefs the schema itself defines as local: `fontSize`, `autoSearch`, `hideStatusRemovalConfirmation`, `statusRemovalCountKey`, `lastSelectedFilter`. Losing them is cosmetic; all user-owned data (shows, My Data, cloud settings) lives in Supabase.

## 5. Data Model & Migrations (Supabase / Postgres)

### 5.1 `shows` — the user's copy of a catalog item + overlay

Primary key: `(namespace_id, user_id, id)` where `id` is the catalog item id (string, e.g. `"tv-1396"` / `"movie-603"` — type-prefixed to avoid TMDB id collisions between movies and TV).

```sql
create table shows (
  namespace_id      text        not null,
  user_id           text        not null,
  id                text        not null,          -- type-prefixed catalog id
  title             text        not null,
  show_type         text        not null check (show_type in ('movie','tv','person','unknown')),
  external_ids      jsonb,                          -- e.g. {"tmdb":"1396","imdb":"tt0903747"}

  overview          text,
  genres            text[]      not null default '{}',   -- names, not ids
  tagline           text,
  homepage          text,
  original_language text,
  spoken_languages  text[]      not null default '{}',
  languages         text[]      not null default '{}',

  poster_url        text,
  backdrop_url      text,
  logo_url          text,
  network_logos     text[]      not null default '{}',   -- reserved

  vote_average      double precision,
  vote_count        integer,
  popularity        double precision,

  last_air_date     timestamptz,
  first_air_date    timestamptz,
  release_date      timestamptz,

  runtime           integer,
  budget            bigint,
  revenue           bigint,

  series_status     text,
  number_of_episodes integer,
  number_of_seasons  integer,
  episode_run_time  integer[]   not null default '{}',
  last_episode_run_time integer,                    -- reserved

  my_tags           text[]      not null default '{}',
  my_tags_update_date    timestamptz,
  my_score          double precision,
  my_score_update_date   timestamptz,
  my_status         text check (my_status in ('active','next','later','done','quit','wait')),
  my_status_update_date  timestamptz,
  my_interest       text check (my_interest in ('excited','interested')),
  my_interest_update_date timestamptz,

  ai_scoop          text,
  ai_scoop_update_date   timestamptz,

  details_update_date    timestamptz,
  creation_date     timestamptz not null default now(),
  is_test           boolean     not null default false,

  provider_data     jsonb,                          -- { countries: { US: { flatrate:[...], rent:[...], buy:[...] } } }

  primary key (namespace_id, user_id, id)
);
create index shows_ns_user_status on shows (namespace_id, user_id, my_status);
```

Notes:
- "In collection" ≡ row exists with `my_status is not null`. Enforced invariant: **a `shows` row only exists while the show is in the collection** (removal deletes the row, clearing all My Data per PRD §5.4). Rows are never created status-less.
- Transient catalog data (cast, crew, seasons, videos, images, recommendations, similar) is **never persisted** — fetched live from the catalog per the storage schema's transient list.
- All five per-field timestamps are stored, powering sort, sync conflict resolution, and Scoop freshness.
- `is_test` supports destructive-test data creation inside a namespace (rider §7).

### 5.2 `cloud_settings` — synced settings

```sql
create table cloud_settings (
  namespace_id   text not null,
  user_id        text not null,
  id             text not null default 'globalSettings',
  user_name      text not null,           -- random friendly name on first launch
  version        double precision not null, -- epoch seconds; conflict resolution
  catalog_api_key text,                    -- optional user-entered; env preferred
  ai_api_key      text,                    -- optional user-entered; env preferred
  ai_model        text not null,
  primary key (namespace_id, user_id, id)
);
```

Conflict rule: newest `version` wins (last-write-wins at record level, matching the reference `CloudSettings`).

### 5.3 `app_metadata` — model-version tracking per namespace

```sql
create table app_metadata (
  namespace_id       text primary key,
  data_model_version integer not null default 3
);
```

### 5.4 Migrations & seed (C6)

- Supabase CLI SQL migrations in `supabase/migrations/` — the canonical, deterministic schema definition. Works against hosted (primary path, `supabase db push` / direct SQL execution) or optional local instance. **Docker is never required**: the documented default is a hosted Supabase project plus migrations applied via CLI or the bundled `npm run db:migrate` script (runs SQL over the connection string).
- `supabase/seed.sql` + `scripts/seed.ts`: optional fixture data (a small library of saved shows for a test user) — used by tests and demos, always written with the current namespace and `is_test = true`.

### 5.5 Data continuity across versions (C14, PRD §5.11)

- `app_metadata.data_model_version` starts at 3 (matching the reference).
- Every future schema change ships as (a) a SQL migration and (b) when shapes change, a data transform migration that carries `my*` fields, scoop, and timestamps forward losslessly.
- The export/backup format (§11.8) doubles as a safety net: export before upgrade is always possible, and the JSON format is versioned.

### 5.6 Local (device) storage

Per the storage schema, these stay client-side (localStorage): `autoSearch` (bool), `fontSize` (`XS…XXL`), `hideStatusRemovalConfirmation`, `statusRemovalCountKey`, `lastSelectedFilter` (`{type, label, value}` JSON, types: `all | genre | myStatus | communityScore | decade | myTag`). All are disposable (C11).

## 6. Identity, Namespace & Environment

### 6.1 Namespace (C7)

- `NAMESPACE_ID` env var, required at boot (fail fast with a clear error if missing). Stable for the lifetime of a build/run.
- The DAL injects `namespace_id` into **every** query — there is no code path that queries without it. A single `scopedDb(namespaceId, userId)` factory returns query helpers pre-bound to the partition; raw table access is lint-banned outside the DAL.
- Reset tooling (§12.4) deletes only rows matching the current namespace.

### 6.2 User identity (C8, C9, C10)

- `user_id`: opaque string. Default from `DEFAULT_USER_ID` env (e.g., a fixed UUID for the benchmark run).
- **Dev identity injection:** server middleware resolves the effective user as:
  1. `X-User-Id` request header — honored only when `AUTH_MODE=dev` (i.e., dev/test),
  2. else `DEFAULT_USER_ID`.
- When `AUTH_MODE=production`, the header path is disabled and the middleware expects a real session (future Supabase Auth / OAuth). Because every table already keys on `user_id` and identity resolution is one middleware function, adopting OAuth later = swap the resolver + add RLS policies. **No schema change.**
- Documented in README (how to inject a user for testing; how it's gated).

### 6.3 Environment interface (C3, C13)

`.env.example` (names + comments; committed):

```
NAMESPACE_ID=            # required: stable id partitioning all persisted data for this build/run
DEFAULT_USER_ID=         # required: opaque user id used when no identity is injected
AUTH_MODE=dev            # dev | production — gates X-User-Id header injection

NEXT_PUBLIC_APP_NAME=    # optional display name

SUPABASE_URL=            # Supabase project URL (server-only usage)
SUPABASE_SERVICE_ROLE_KEY=  # server-only; never exposed to the browser
# SUPABASE_ANON_KEY=     # unused by default (browser never talks to Supabase); present for future RLS mode

CATALOG_API_KEY=         # external catalog (TMDB) API key — server-only
AI_API_KEY=              # AI provider key (benchmark mode) — server-only
AI_MODEL=                # default AI model id
AI_BASE_URL=             # optional override for provider endpoint
```

`.gitignore` excludes `.env*` except `.env.example`. Env parsed once through a Zod schema in `src/config/env.ts`; the app refuses to boot with missing/invalid required vars. **No source edits needed to configure a run.**

### 6.4 Scripts (C5)

```
npm run dev          # start app (Next.js dev)
npm run build/start  # production build/serve
npm test             # unit + integration (Vitest)
npm run test:e2e     # Playwright journeys
npm run test:reset   # delete all rows for NAMESPACE_ID (optionally only is_test=true via flag)
npm run db:migrate   # apply migrations to configured Supabase
npm run seed         # optional fixtures into current namespace
```

## 7. Server API Surface

All routes under `/api`, all resolve identity via middleware, all validate payloads with Zod. User-data routes return the **overlaid** show shape so every client surface renders user data consistently (PRD display rule).

### 7.1 Library (user data)

| Route | Method | Behavior |
|---|---|---|
| `/api/library` | GET | All saved shows for (ns, user). Supports filter params (tag, genre, decade, scoreRange, myStatus, mediaType) — though primary filtering is client-side over the cached library. |
| `/api/library/:id` | GET | One saved show (or 404 → not in collection). |
| `/api/library/:id` | PUT | Upsert with **field-level intents**: `{ setStatus?, setInterest?, setScore?, setTags?, catalogSnapshot? }`. Server applies domain rules (saving triggers, defaults, timestamps, merge engine) — clients never write raw rows. |
| `/api/library/:id` | DELETE | Remove from collection: deletes the row (clears all My Data + scoop) per PRD §5.4. |
| `/api/library/:id/scoop` | POST | Generate Scoop (streaming). Persists to row only if show is in collection; returns cached scoop if fresher than 4h unless `force`. |
| `/api/tags` | GET | Distinct tag list for the user (drives sidebar tag filters + tag picker). |

**Upsert semantics (domain rules, D4):**
- Any intent on an unsaved show creates the row (saving triggers, PRD §5.2).
- Defaults: no explicit status → `later` + `interested`; **first save via rating → `done`** (PRD §5.3).
- Setting `interested`/`excited` chip → `myStatus='later'` + `myInterest=…` (PRD §4.2).
- Status moves away from Later: interest is **retained** in the row but treated as irrelevant (PRD §4.3) — grouping logic ignores it unless status is Later.
- Each changed `my*` field stamps its own `*_update_date = now()`.
- Re-save/merge: `my*` fields resolve newest-timestamp-wins; public fields via `selectFirstNonEmpty` (never overwrite non-empty with empty/nil); `details_update_date := now()`; `creation_date` immutable (storage-schema merge policy).

### 7.2 Catalog (proxy over CatalogProvider; keeps keys server-side)

| Route | Method | Behavior |
|---|---|---|
| `/api/catalog/search?q=&type=` | GET | Title/keyword search → grid results, each merged with library overlay flags (in-collection, rating). |
| `/api/catalog/shows/:id` | GET | Full detail payload: canonical fields + transient extras (credits, seasons, videos, images, providers, recommendations/similar). If saved, server merges into the stored row (merge engine) and returns overlaid result. |
| `/api/catalog/person/:id` | GET | Person: bio, images, combined credits (for filmography + analytics). |
| `/api/catalog/resolve` | POST | Batch-resolve AI outputs: `[{title, externalId?, mediaType}]` → real shows. Lookup by external id when present; accept first result whose title matches case-insensitively; else fuzzy title search; unresolved entries flagged for non-interactive rendering/Search handoff (PRD §5.8, quality bar "real-show integrity"). |

### 7.3 AI

| Route | Method | Behavior |
|---|---|---|
| `/api/ai/ask` | POST (stream) | Chat turn. Input: visible turns + rolling summary + optional seed show ("Ask about this show") + taste profile. Output: streamed commentary, then structured `showList` block parsed server-side; response ends with resolved mentioned-shows payload. |
| `/api/ai/summarize` | POST | Summarize older turns into 1–2 persona-preserving sentences (triggered ~10 messages, §9.4). |
| `/api/ai/concepts` | POST | Input: 1..n shows. Output: bullet-list concepts (8 single / 12 multi), validated 1–3 words, de-generified, ordered by strength; multi-show concepts must be shared across all inputs. |
| `/api/ai/recommend` | POST | Input: selected concepts (1–8) + source shows + taste profile. Output: **5** recs (Explore Similar) or **6** (Alchemy), each with a 1–3 sentence reason naming the matched concepts; server resolves to real shows before returning. |
| `/api/ai/starters` | GET | 6 random starter prompts from the authored pool (refreshable). |

AI persistence policy (PRD §5.7): only Scoop persists (and only for in-collection shows, 4h freshness). Ask history, mentioned-shows strip, and Alchemy results are session-state only — held in client memory, cleared on leave/reset.

### 7.4 Data & test utilities

| Route | Method | Behavior |
|---|---|---|
| `/api/export` | GET | Streams a `.zip` containing `backup.json` — all saved shows + My Data + cloud settings, dates ISO-8601, format versioned. |
| `/api/test/reset` | POST | Dev/test-gated (`AUTH_MODE=dev` only). Deletes rows for current namespace (flag: only `is_test`). Backs `npm run test:reset`. |
| `/api/settings` | GET/PUT | Cloud settings (username, ai model, optional keys) with `version` LWW conflict handling. |

## 8. Catalog Integration & Merge Engine

### 8.1 `CatalogProvider` interface (D3)

```
searchShows(query, type?) → ShowSummary[]
getShowDetails(id) → { show: Show, transient: { cast, crew, seasons, videos, images, recommendations, similar, providers } }
getPerson(id) → Person
findByExternalId(externalId, mediaType) → ShowSummary | null
```

TMDB adapter responsibilities (all invisible above the interface): genre id → name mapping; image path → full URL construction; **best-logo selection deterministic rule** (highest-rated, prefer English — matching the schema note); multi-format date parsing; media-type inference (`name` → tv, `title` → movie, else reject as `unknown`); provider payload → IDs-only `ProviderData` by region; type-prefixed id construction.

### 8.2 Merge engine (pure functions, exhaustively tested)

`mergeCatalogIntoStored(fresh, stored) → merged` implementing exactly the storage-schema policy:
- public fields: `selectFirstNonEmpty(new, old)` — empty string/array/nil never clobbers data;
- `my*` fields: per-field newest-timestamp wins (both dated → newer; one dated → that one);
- `ai_scoop` treated like a my-field (timestamped);
- `details_update_date := now()`, `creation_date` preserved.

This same function serves catalog refreshes **and** future sync/duplicate-merge (PRD §5.10) — one rule set, one test suite.

## 9. AI Subsystem

### 9.1 Provider adapter

`AIProvider.chat({ system, messages, stream?, temperature? })` — default Anthropic adapter; model id from settings/env. Retries/timeouts at the adapter; all prompt construction above it. User-entered keys (Settings) override env at request time; never logged, never committed.

### 9.2 Persona layer (single source of truth)

`src/server/ai/persona.ts` encodes the shared persona (fun chatty TV/movie nerd; joy-forward; opinionated honesty; vibe-first spoiler-safe; specific not generic; short-by-default) and the tone sliders (70/30 friend-critic, 60/40 hype-measured, adaptive playfulness). Every surface prompt composes persona + surface mode + task contract, so voice consistency is structural, not copy-pasted. Shared hard rules in every prompt: stay in TV/movie domain (redirect otherwise); spoiler-safe unless explicitly invited; honest about mixed reception; never recommend without a reason.

### 9.3 Taste-profile builder

Serializes the user's library into compact AI context: titles + status + interest + rating + tags (bounded — cap items, prioritize recently updated via the `*_update_date` fields). Used by Ask, Alchemy recs, Explore Similar recs. This is what makes discovery "taste-aware" (PRD §8.3).

### 9.4 Surface contracts (from `ai_prompting_context.md` + quality bar)

| Surface | Input | Output contract | Numbers |
|---|---|---|---|
| **Ask** | turns + summary + taste profile (+ seed show) | `{commentary, showList}`; commentary friend-in-dialogue, direct answer in first 3–5 lines, bullets for multi-recs, no external IDs in commentary; `showList` = `Title::externalId::mediaType;;…` | — |
| **Scoop** | show context (+ collection status) | streamed mini blog post: personal take → honest stack-up vs reviews → **The Scoop** centerpiece → fit/warnings → "Worth it?" verdict | 150–350 words |
| **Concepts** | 1 show (Explore Similar) or 2+ shows (Alchemy) | bullet list only; 1–3 words each; evocative, spoiler-free, no explanations; multi-show = shared across **all** inputs; diverse axes (structure/vibe/emotion/dynamics/craft); ordered by strength; generic concepts rejected | 8 single / 12 multi; select ≤8 |
| **Concept recs** | selected concepts + sources + taste | list of `{title, externalId, mediaType, reason}`; reasons 1–3 sentences naming matched concepts; recent-bias, classics allowed | 5 (Explore Similar) / 6 (Alchemy) |
| **Summarization** | older chat turns | 1–2 sentences, same persona voice (no sterile system tone) | after ~10 messages |

**Parsing & fallbacks (D6):** structured output validated (Zod + protocol parser). On failure → one retry with stricter format instructions → fallback to plain commentary + Search handoff. A post-generation validator also rejects/regenerates generic concepts (blocklist: "good characters", "great story", "funny", bare genres…) and enforces the 1–3-word rule.

**Starter prompts:** author a pool (~40–80) in persona voice, stored as data in `src/config/starterPrompts.ts`; welcome view samples 6, refresh re-samples.

### 9.5 Show-resolution pipeline (quality bar: real-show integrity = non-negotiable)

For every AI-emitted show: (1) `findByExternalId` when id present → verify case-insensitive title match; (2) else title search → first case-insensitive match; (3) resolved → real selectable Show (+ transient AI reason), overlaid with user data if saved; (4) unresolved → non-interactive chip with "Search for this" handoff. Resolution happens server-side so clients only ever receive actionable payloads.

### 9.6 Quality bar integration

`discovery_quality_bar.md` becomes a lightweight eval harness (not CI-blocking): scripted scenarios producing outputs scored manually on the 0–2 rubric (voice ≥1, taste ≥1, real-show integrity =2, total ≥7/10). Golden-set capture template included for future regression protection. Deterministic contract aspects (counts, word limits, structured format, resolution) **are** CI-tested against a mocked provider.

## 10. Frontend Application (Fractal Architecture)

### 10.2 Global layout & navigation (PRD §6)

Persistent shell: filters/navigation panel + main content area; persistent **Find** and **Settings** entries. Routes: `/` (Home), `/find` (`?mode=search|ask|alchemy`), `/show/[id]`, `/person/[id]`, `/settings`. "Search on launch" pref redirects to `/find?mode=search` on boot.

### 10.3 The overlay rule, implemented once

`useShowOverlay(show)` merges any catalog-shaped item with the library cache so **every** tile/strand/mention renders user data (badges: in-collection, rating) consistently — Home, Search, AI strips, recommendations, filmography. Single implementation ⇒ the display rule can't drift by surface.

### 10.4 Filter model (domain)

`filterModel` evaluates `FilterConfiguration` (`all | myTag | genre | decade | communityScore | myStatus`) + media-type toggle over the library; sidebar derives tag filters from user tags (plus "No tags" when tagless shows exist) and data filters from library contents. Last selection persists to localStorage (`lastSelectedFilter`). (`myStatus` filters supported by the model; surfacing in sidebar stays an optional extension, per PRD open questions.)

### 10.5 Session-state stores

Ask and Alchemy session state (turns, summary, mentioned shows, picked shows, concepts, results) live in client memory stores (Zustand or reducer-in-context), deliberately **not** persisted — matching PRD §5.7 — and cleared on leave/reset.

## 11. Feature Implementation Details

### 11.1 Collection Home

- Status-grouped shelves in fixed order: **Active** (prominent, larger tiles) → **Excited** (Later+Excited) → **Interested** (Later+Interested) → **Others** (collapsed group: Wait, Quit, Done, and Later items missing interest). Hidden `next` status: rows may carry it (model supports), grouped under Others; not surfaced as a chip.
- Within groups, sort by most-recent `my_status_update_date` (recently-updated-first, PRD §5.6).
- Media-type toggle composes with the active filter. Tiles: poster, title, badges.
- Empty states: empty collection → prompt to Search/Ask (deep-links to Find modes); filter miss → "No results found."

### 11.2 Search (Find → Search)

- Debounced live query → `/api/catalog/search` → poster grid with overlay badges. Tap → Detail. No AI voice. Auto-open via `autoSearch` pref. Also serves as the handoff target for unresolved AI titles (pre-filled query).

### 11.3 Ask (Find → Ask)

- Welcome: 6 random starters + refresh. Chat thread with streamed assistant turns.
- Each turn calls `/api/ai/ask` with visible turns + rolling summary + taste profile; after ~10 messages, older turns are summarized via `/api/ai/summarize` and folded into context (persona-voice summaries).
- Mentioned shows: parsed `showList` → resolved shows → horizontal strip below the thread; tap → Detail; unresolved → Search handoff chip.
- **Ask about a show:** Detail CTA navigates to Find/Ask with a seed show; conversation context is seeded with that show (greeting acknowledges it). Exact prefill copy is TBD in the PRD — decision: assistant opens with a one-line in-persona invitation about the show.
- Reset conversation control clears thread + summary + strip.

### 11.4 Alchemy (Find → Alchemy)

- Step cards: **1) Pick 2+ shows** (search across global catalog with library items surfaced/marked) → **2) "Conceptualize Shows"** → shared-concept chips (12 offered, select 1–8) → **3) "ALCHEMIZE!"** → 6 recs with concept-citing reasons → **4) "More Alchemy!"** chains results as new inputs.
- Backtracking invariant (state machine): changing show selection clears concepts + results; changing concept selection clears results.
- Copy nudges: "pick the ingredients you want more of"; empty-state nudge to select ≥1 concept. Session-only persistence.

### 11.5 Show Detail

Section order preserved exactly (Detail experience spec §3): header media carousel (trailers when available, graceful poster/logo fallback; inline playback) → core facts + community score → tag chips → overview + Scoop → "Ask about this show" → genres/languages → recommendations strand → Explore Similar → Stream It (providers) → Cast → Crew → Seasons (TV only) → Budget vs Revenue (movies, when available).

- **Relationship toolbar (not in scroll body):** chips `Active / Interested / Excited / Done / Quit / Wait`. Interested/Excited set Later+interest. Reselecting the active chip → removal confirmation dialog (destructive: clears all My Data) with "stop asking" suppression after repeated removals (`statusRemovalCountKey`, `hideStatusRemovalConfirmation`).
- **Rating bar:** rating an unsaved show auto-saves as **Done**; clearing rating on a saved show sets `my_score = null` (open question noted — no explicit Unrated state in v1).
- **Tags:** picker sources the user's tag library + free entry; adding a tag to an unsaved show auto-saves **Later + Interested**.
- **Scoop:** toggle copy state machine — "Give me the scoop!" (none) / "Show the scoop" (cached) / "The Scoop" (open); streams progressively with "Generating…" affordance; 4h freshness (regenerate on demand after expiry); persists only if in collection, else ephemeral for the session.
- **Explore Similar:** "Get Concepts" → 8 chips → select 1+ (cap 8) → "Explore Shows" → 5 resolved recs with reasons; 1-line "why concepts matter" explainer under the CTA (spec TODO adopted).
- On load, server merges fresh catalog details into any stored row (merge engine) — public data refreshes, user data survives.
- Critical states covered: unsaved show (all auto-save triggers live), no trailers/backdrops (premium poster/logo fallback), no concepts yet (CTA only), TV vs movie section variance.

### 11.6 Person Detail

Image gallery + name + bio; analytics charts (average project ratings, top genres, projects-by-year) computed from combined credits; filmography grouped by year (newest first); credit tap → Show Detail (overlaid if saved).

### 11.7 Settings

- **App:** font size (XS–XXL → theme type scale), search-on-launch.
- **User:** username (random friendly default on first launch; synced via `cloud_settings`).
- **AI:** provider key (env-first; user-entered optional, stored server-side, never committed), model selection.
- **Integrations:** catalog key (same policy).
- Cloud settings LWW by `version`.

### 11.8 Export / Backup

"Export My Data" → server streams `.zip` containing versioned `backup.json`: all saved shows with full My Data + timestamps + scoop, cloud settings; **all dates ISO-8601**. Import/Restore: out of scope v1 (PRD open question) but the format is designed round-trippable so restore is a follow-on, not a redesign.

## 12. Testing & Quality Strategy

### 12.1 Unit (Vitest, adjacent to source)

Highest-value targets — the domain module:
- **Saving rules matrix:** every trigger × prior state → resulting status/interest/timestamps (incl. rate-unsaved→Done, tag-unsaved→Later+Interested, chip semantics, interest retention off-Later).
- **Merge engine:** `selectFirstNonEmpty` cases (empty string/array/nil never clobber), per-field timestamp resolution, `creation_date` immutability, `details_update_date` refresh.
- **Removal semantics:** row deletion clears everything; confirmation-suppression counter logic.
- **Parsers/validators:** `showList` protocol (well-formed, malformed, empty, delimiter edge cases), concept validator (word count, generic blocklist), filter model, taste-profile bounding.

### 12.2 Integration (Vitest against a test namespace)

API-route tests on a real (hosted or local) Supabase using a dedicated `NAMESPACE_ID` per run/CI job: library CRUD + rule application, catalog merge on detail fetch, settings LWW, export content, reset endpoint scoping (create in ns-A, reset ns-B, assert ns-A intact — directly proving C7/C12). AI routes tested with a **mocked provider** for contract shape, counts, retry/fallback behavior.

### 12.3 E2E (Playwright)

The PRD's ten key journeys, headline flows: build-collection (search→status→tag→rate), rate-to-save, tag-to-save, filter-driven Home, Ask discovery→save, Explore Similar round, full Alchemy chain, talent deep-dive, backup export, removal confirmation + suppression. AI mocked at the provider boundary for determinism; identity injected via `X-User-Id`; each run uses a fresh namespace and `npm run test:reset` teardown.

### 12.4 Destructive-test compliance (C7, C12)

Test data written with `is_test=true` where applicable; `test:reset` deletes by namespace (optionally test-only rows); no global teardown anywhere. CI generates a unique namespace per pipeline run to guarantee zero collisions between concurrent runs.

### 12.5 AI quality (manual bar, per §9.6)

Eval script + rubric doc; run before release and after prompt/model changes. Non-CI-blocking; golden-set capture template ready to populate.

### 12.6 Visual & lint

Strict TS + ESLint (incl. custom rule/discipline: no raw hex/px in TSX, no direct DAL imports outside server). Component visual states via Storybook or Playwright screenshots for tiles, chips, Scoop states, and empty states (per INSTRUCTIONS.md "visual testing highly preferred").

## 13. Delivery Phases

Ordered to de-risk: platform/isolation first, then the rules engine everything depends on, then surfaces from core to AI-rich. Each phase lands lint-clean with its tests.

*Exit:* app boots against hosted Supabase; reset scoped to namespace proven by test.

**Phase 1 — Domain core + catalog adapter**
Domain module (saving rules, merge engine, status/filter models) fully unit-tested; TMDB adapter (search, details, person, providers, genre/image/logo mapping); `/api/catalog/*`, `/api/library/*`, `/api/tags` with rule enforcement.
*Exit:* rules matrix green; save/merge/remove verified end-to-end via API tests.

**Phase 2 — Home + Search + Detail (non-AI)**
Home shelves + filter sidebar + media toggle + empty states + tile badges; Search grid with overlay + autoSearch; Detail with full section order, relationship toolbar, rating/tags auto-save, removal confirmation + suppression, seasons/budget-revenue variance, providers, recommendations strand; Person page.
*Exit:* journeys 1–5, 9 pass e2e; overlay rule verified across surfaces.

**Phase 3 — AI foundation + Scoop**
AIProvider adapter + persona layer + taste-profile builder; parsing/retry/fallback framework; resolution pipeline + `/api/catalog/resolve`; Scoop streaming end-to-end with cache/freshness/persistence rules and toggle-copy states.
*Exit:* Scoop meets structure/length contract; unsaved-show ephemerality verified.

**Phase 4 — Ask**
Chat UI + streaming; starter pool + welcome; mentions protocol → strip → Detail/Search handoff; ~10-message summarization; Ask-about-show seeding; session reset semantics.
*Exit:* journey 6 passes; parse-failure fallback verified.

**Phase 5 — Concepts: Explore Similar + Alchemy**
Concepts endpoint + validator (8/12, shared-across-all, generic rejection); Explore Similar on Detail (5 recs); Alchemy flow with step cards, 8-cap selection, 6 recs, chaining, backtracking-clears-downstream state machine.

**Phase 6 — Settings, export, hardening**
Settings surfaces + cloud-settings sync (LWW); export zip; font-size theme integration; error/loading/empty polish; AI quality-bar eval pass; accessibility sweep; docs finalization (env, scripts, identity, namespace, reset, OAuth migration path).
*Exit:* rider success-criteria checklist (§2) fully green; journey 10 passes.

**Dependencies:** 0 → 1 → 2 → (3 → 4, 3 → 5) → 6. Phases 4 and 5 can proceed in parallel after 3. Person page can slide within 2–6 if needed (no downstream dependents).

## 14. Risks & Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| AI structured-output flakiness (`showList`, concept format) | Broken mentions/concepts UX | Strict server-side parse + single retry + graceful fallback path (designed in, D6); provider-mocked contract tests; validator regenerates bad concepts |
| Hallucinated/unresolvable titles | Violates non-negotiable real-show integrity | Server-side resolution pipeline; unresolved → non-interactive + Search handoff; quality-bar evals |
| Merge-rule subtlety (empty-vs-nil, per-field timestamps) | Silent user-data loss — worst-case product failure | Pure-function merge engine with exhaustive table-driven unit tests before any UI exists (Phase 1) |
| Namespace leakage in some query path | Benchmark run collisions | Single DAL choke point; scoped-client factory; lint ban on raw table access; cross-namespace integration test |
| Dev identity header abused in prod mode | Security hole later | `AUTH_MODE` gate tested both ways; documented |
| TMDB rate limits / hiccups during runs | Flaky tests, slow pages | Server-side short-TTL caching of catalog GETs; e2e mocks provider; graceful degraded states |
| Scoop/Ask streaming complexity on the Next.js boundary | Blank-wait UX regressions | Standard streamed route handlers + one shared `StreamingText` component; "Generating…" affordance specified |
| Voice drift across surfaces | Loses the product's "heart" | Single persona module composed into every prompt; quality-bar rubric checks voice ≥1 |
| Missing 80-prompt pool & prompt cookbook | Gap vs reference feel | Author pool + prompts against the behavioral contracts (the docs are explicitly rebuild-parity oriented, not verbatim-prompt oriented) |
